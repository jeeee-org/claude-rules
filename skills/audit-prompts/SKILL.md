# audit-prompts — 指示の負債を監査する

モデルが替わった時や、指示が膨らんできた時に回す。**監査だけを行い、ファイルも設定も書き換えない**（例外は最後の段で、利用者が選んだ指摘を`IMPROVEMENTS.md`へ送ることだけ）。読んだ文書は証拠として扱い、書き換えの許可とは受け取らない。**十分に絞れている設定なら「直す所はない」と言う。直す所を作り出さない。**

**問い方**：Claude CodeならAskUserQuestionで選択肢を出す。使えない環境（Codex等）では、番号付きの選択肢を出して答えを待つ。

## 0. 準備

1. **cloneの場所**：いまの作業ディレクトリが`rules/common-rules.md`を持てばそこ。無ければ`clone=$(dirname "$(readlink -e ~/.claude/skills/init-rules/IMPROVEMENTS.md)")`（Codexなら`~/.codex/skills/init-rules/IMPROVEMENTS.md`）。cloneで`git pull --ff-only`してから読む（古い正本を監査しないため）。
2. **何のための監査か**を1行で決める。利用者の言葉にあれば聞かない。例：「<新しいモデル名>への更新」「常時読み込みの量が増えた」。モデルの更新なら、前のモデルの名前も控える（古い癖かを判定する物差しになる）。
3. **そのPJの使い方**：どこで起動し、どこを編集するかを、記録（`AGENTS.md`・`README.md`等）か利用者の言葉で確かめる。読み込まれるものは起動する場所で決まるので、コメントやスクリプトの想定で決めない。
4. **見る範囲**：既定は次の3つ全部。利用者が絞れば従う。

| 行き先 | 見るもの | 直す場所 |
|---|---|---|
| 正本（全PC・全PJに効く） | `$clone/rules/common-rules.md`・`$clone/skills/*/SKILL.md`・`$clone/hooks/*`・`$clone/settings/*.json` | このリポ。`IMPROVEMENTS.md`経由で正本のPCが直して配る |
| このPC | `~/.claude/settings.json`（思考の強さ`effortLevel`・モデルごとの`modelSettings`・許可・フック）・`~/.claude/CLAUDE.md`・`~/.claude/rules/`（`paths:`の無いものは常に読み込まれる）・`~/.claude/agents/`・claude-rules以外のスキル。Codexなら`~/.codex/config.toml`・`~/.codex/AGENTS.md` | このPCの設定。全PCで揃えるべきものは正本の`settings/`へ |
| このPJ | `AGENTS.md`の**共通ルールのブロックの外**・`.claude/rules/`・上位のディレクトリの`AGENTS.md`・`CLAUDE.md`（起動した場所より上も読み込まれ、上位に`CLAUDE.md`があると`AGENTS.md`が読まれなくなる）・PJの下のディレクトリの`AGENTS.md`（そこのファイルを読んだ時に追加で載る。PJの中にworktreeを置くと本体の分と二重になり、`.claude/settings.json`の`claudeMdExcludes`に`**/worktrees/**/AGENTS.md`を入れると止まる）・`.claude/settings.json`・`.claude/skills/`・`.claude/agents/`・ループのひな型を入れていれば`.claude/loop/` | そのPJ（そのPJの規約で） |

- **PJの`AGENTS.md`にある共通ルールのブロックは見ない**。正本からの複製なので、指摘は正本（`rules/common-rules.md`）の行で書く。ブロックと正本の食い違いは`python3 $clone/tools/embed-rules.py --scan <親ディレクトリ>`の「古い」で分かり、負債ではなく反映漏れ。
- 他のリポが配るもの（quorum等）の指摘は、そのリポの改善メモへ回す。
- 資格情報のファイルは丸ごと読まない（`settings.json`はキーを絞って`jq`で読む）。

## 1. 地図を作る

見る範囲のものを並べ、それぞれを次の3つに分ける。**バイト数を添える**（`wc -c`）。

- **常に読み込まれるもの**：共通ルールのブロック・PJ固有の`AGENTS.md`・`paths:`の無い`rules/*.md`・各スキルの説明（frontmatterの`description`。無ければ本文の1行目が説明になる）・設定。スキルの一覧はコンテキストの1%が上限で、超えると使われていないものから説明が落ちる。**一覧の確かめは普段と同じモデルで行う**（小さいコンテキストのモデルでは落ちて見え、誤る）
- **呼ばれた時だけ読まれるもの**：スキルの本文・エージェントの定義・参照されるファイル
- **機械が効かせるもの**：フック・関門・許可の設定（モデルの判断に頼らない）

あわせて、同じ指示が複数の場所にあるか（重複）、どちらが優先するか（優先順位）を書き留める。上限は各PJのルートで`.claude-rules/check-limits.sh`を実行して見る（共通ルールを書き込んだPJにある）。

## 2. 5つの層を見る

層は①スキルの`description`②スキルの本文③`AGENTS.md`とエージェントの定義④思考の強さと許可の設定⑤終わりの条件。次の型に当たる行を拾う。

| 型 | 例 | 見方 |
|---|---|---|
| 古いモデル向けの思考の指示 | 「よく考えて」「ステップごとに考えて」「think step by step」 | 新しいモデルでは既定で考えるので、トークンを使うだけ |
| 推論の書き出しを求める指示 | 「理由を先に書いてから答えよ」「思考を出力せよ」 | 応答が長くなるだけで、判断の質は上がらない |
| 前のモデルから引き継いだ思考の強さ | `effortLevel`・`model_reasoning_effort`・スキルやエージェントの定義にある固定値 | いつ・何のために決めた値かを見る。理由が前のモデルの弱さなら候補。**新しいモデルで効いているかも見る**（Opus 5.5は最上位の`effortLevel`を読まず、`modelSettings.<モデルID>.effortLevel`だけを読む） |
| 権限の曖昧さ | 「必要なら」「適宜」「状況に応じて」で、誰が決めるか書いていない | 止まるべき所で進む／進むべき所で止まる、のどちらかを生む |
| 早すぎる停止 | 毎段で確認を求める・「一度止まって報告」の多用 | 長い自律の作業が細切れになる |
| 終わりの条件の欠け | 何をもって完了とするか書いていないスキル・エージェント | 早く止まるか、止まらないか |
| 自律性とぶつかる統制 | モデルが既定で上手くやることの手順化 | 残すと手順の遵守にトークンを割く |
| スキルの説明の欠け（層①） | frontmatterが無い・`description`に「いつ使うか」が無い・本番や外へ出すスキルに`disable-model-invocation: true`が無い | 呼ばれるべき時に呼ばれない／本番のデプロイなどをモデルが自分で呼べてしまう |
| 食い違い | 2か所で逆のことを言う指示 | どちらが勝つかを書き、片方を消す案にする |
| 重複 | 同じ指示が常時読み込みの2か所以上にある | 常時読み込みの側から消す案を優先する |

**残すもの**（指摘しない）：ビルド・検証のコマンド、構造の決まり、正確な手順、非自明な約束事、安全策（フック・関門・外への副作用の前で止まる決まり）。**`REQUIREMENTS.md`で日付付きで決めた運用**（記録のカード・checkpoint・コミットの決まり・応答の書き方など）は負債として消す案にせず、変えるなら「決定の見直しの提案」として理由を添えて別に出す。Claude Code自身が入れる指示（システムプロンプト）は直せないので対象外。

## 3. 紙の上で5つの場面を通す

実際には動かさない。場面ごとに「依頼 → 効く指示 → 思考の強さ → 読まされるもの → 行動 → 許可 → 止まる条件」をたどり、引っかかった所を2の指摘に結びつける。

1. 一行の修正
2. 複数ファイルにまたがる作り直し
3. 長い自律の作業（ループ・夜間の実行）
4. 時間の予算がある作業
5. サブエージェントへの並列の振り分け

## 4. 報告する

次の順で出す。**番号や記号だけで指さない**（何の指摘か日本語で書き、記号は後ろに添える）。

1. **影響の大きい順の指摘**。1件ごとに：行き先（正本／このPC／このPJ）・場所（パスと見出し。行番号だけで指さない）・**消すか書き換える行をそのまま引用**・書き換えるなら新しい文・理由1文。**確定（文書に証拠がある）と仮説（場面を通して推したもの）を分けて並べる**
2. **見られなかった所**（読めなかったファイル・範囲外にしたもの）
3. **5つの場面の通し**（場面ごとに数行）
4. **行き先ごと・ファイルごとの直し案**。常時読み込みの上限を超える・迫る時は、削る前に、特定のディレクトリで作業する時だけ要る決まりを`.claude/rules/*.md`へ移し`paths:`（PJルートからの相対glob。例`repos/**`）を付けて、そこのファイルを読んだ時だけ載せる手を候補に挙げる
5. **最初にやる最小の束**（1回のcommitで入る大きさ。常時読み込みを減らすものと、食い違いを消すものを優先）
6. **良くなったかの確かめ方**（直す前後のバイト数・`check-limits.sh`・正本を直したら`python3 -m unittest discover -s $clone/tools/tests`・同じ場面をもう一度通す）

## 5. 行き先へ送る（利用者が選んだ分だけ）

報告のあと、どれを送るかを利用者に選んでもらう。**選ばれなかったものは送らない。**

- **正本行き** → `IMPROVEMENTS.md`へ追記する（`init-rules`の「改善案の記録」に従う：`readlink -e`でリンクを確かめる・末尾へ追記・公開リポなので業務PJの内部名や具体値は書かず動作で書く）。形：

  ```markdown
  ## YYYY-MM-DD — 指示の見直し（<何のための監査か>・<出どころのPJの種類>）
  - [<正本のパスと見出し>] 「<消すか書き換える行の引用>」／<理由1文>／<書き換え案>（確定|仮説）
  ```

  追記したらcloneでその1ファイルだけをcommitしてpushする（正本は直さない。直すのは正本のPC。README「ルールを変更するとき」）。**そのPCがcloneへの書き込みを禁じている時**（閲覧専用のPC）は、追記もcommitもせず、追記する本文をコードブロックで出す（利用者が正本のPCへ渡す）。
- **このPC行き** → 直し方（`settings.json`の差分など）を示し、当てるかは利用者が決める。**全PCで揃えるべき値**（思考の強さの既定など）なら、正本の`settings/`へ入れる案として正本行きにも1件足す。
- **このPJ行き** → そのPJの`REQUIREMENTS.md`にカードを立てるかを聞く。直しはそのPJの規約で行う。

## 正本のPCでの反映（参考）

正本のPCは`IMPROVEMENTS.md`の「指示の見直し」の項を読み、README「ルールを変更するとき」の手順で直して配る。**`install.sh`は`settings.json`の既にあるキーを上書きしない**ので、全PCの設定の値を変える直しはREADME「日付ごとの一回限りの手当て」に手順を書く。反映した項には`⇒ [反映済み → <直した場所>]`を付ける。
