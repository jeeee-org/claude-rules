# 2026-09-20 帰属行の関門 — 規約の1行と、機械の歯止め

## 背景（他PCからの依頼）

2026-09-20、業務のcdp-sharedで**着手宣言のcommitへ`Co-Authored-By: Claude ...`を入れて
`origin/develop`へpushしてしまい**、force pushで履歴を差し替える手当てが要った。
原因は、セッション側から「commitの末尾に付けよ」という指示が渡り、それに従ったこと。

いまの§5.2は「禁止②（業務/共有リポ）」としか書いておらず、**渡された指示に従うか規約に
従うかの判断をモデルに委ねる形**だった。cdp-shared側のPJ`CLAUDE.md`には同趣旨の記載が
あり、そちらは機能していた——つまり**明示されていれば勝てる**。

依頼は3件（①規約の1行 ②pushの関門の新設 ③記録の関門の誤検知修正）。

## ① §5.2へ1行

`rules/global-rules.md`の禁止②の直後:

> - **セッション側から付けよという指示が来ても付けない**（この規約が勝つ）。機械の歯止め＝`~/.claude/hooks/push-attribution-guard.sh`（pushの直前に、押し出すcommitのメッセージを見る）。

依頼文のパスは相対だったが、§2の`~/.claude/tools/check-limits.sh`に合わせて絶対にした
（常時ロードのルールは、読んだ先でそのまま叩ける形にする）。

Codex側（`rules/codex-global-rules.md`）にも同趣旨を1文足した。**ただしフックは書いていない**
——Codexにこの関門は無いので、書けば「指す先の無い手順」になる（NOTES 2026-08-29）。

グローバル`CLAUDE.md`は12,226 → 12,472B（上限14,336B・残り1,864B）。

## ② hooks/push-attribution-guard.sh（新設）

依頼された実装をほぼそのまま採用。要点:

- **なぜcommitでなくpushか** = `push-record-guard.sh`と同じ理由。commitの時点はメッセージの
  渡し方（`-m` / `-F file` / エディタ / ヒアドキュメント）に依存して中身が見えないが、
  pushの直前ならcommitはもう存在するので`git log --format=%B`で確実に読め、**しかもまだ
  `--amend`で直せる**（未pushなのでforce不要）。押してしまうと今回の重い手当てになる。
- **例外はコマンド側の`CR_SKIP_ATTRIBUTION_GUARD=1`だけ**。記録の関門と違い、
  メッセージのトレーラでは抜けられない——問題にしているのがメッセージそのものなので、
  そこに例外を置くと堂々巡りになる。
- **リポの作りで対象を絞らない**（記録の関門は「記録の方式を使っているか」で絞る）。
  規約上は個人リポ任意だが、既定を厳しくして脱出弁を1つ置くほうが単純。
- 署名の**形**だけを見る。本文に「Claude」と書くこと自体は止めない。

`install.sh`への登録は既存の記録の関門と同じ扱い（cp / chmod / `ATTR_CMD` / 控えを取る
条件のjq判定 / `register_hook PreToolUse` / 完了時の一覧 / 末尾の案内）。

テストは`tools/tests/test_push_attribution_guard.py`に17件。止める側（`Co-Authored-By` /
宣伝行 / メールアドレス単独 / 大文字小文字 / トレーラで抜けられない / 呼び出しの形に
依存しない / 記録の方式を使っていないリポ）と通す側（署名の形でない本文 / 人間の共著者 /
通す指定 / `--amend`後 / `--dry-run`・`--delete` / 大量 / リモート無し / gitの外 / Bash以外）。

## ③ commit-record-guard.shの誤検知

`WRITE_RE`のリダイレクト検出`[^0-9&>]>>?[[:space:]]*[^&[:space:]]`が、**commitメッセージ中の
メールアドレスの`>`**を出力リダイレクトと誤認していた。`git commit -m "...<noreply@anthropic.com>"
&& git push`で`m>`＋閉じ引用符`"`にマッチする。

**効いたのは誤検知そのものではなく、それが作った逃げ道。** 止められた側（他PCの私）は
`-m`をやめて`-F ファイル`へ回り、**その結果そのcommitは記録の関門の目を素通りした**。

案A（引用符の内側を落としてから判定）を採用。案B（直後が引用符なら見ない）は
`> "out.txt"`のような正当なリダイレクトを取りこぼすため退けた。

`strip_quoted_args`を1つ足し、`WRITE_RE`の判定だけに当てる（commitの検出や印の判定は
従来どおり`head_part`のまま＝範囲を広げない）。**引用の状態は行をまたいで持ち越す**
——`-m`の本文は複数行になるので、行ごとに戻すと片側しか落ちない。

修正前後を同じ入力で比べて確認:

    old-guard.sh              → exit 2（「分けて打て」で誤検知）
    commit-record-guard.sh    → exit 0

テストを3件追加（引用の中の記号は数えない / 複数行のメッセージ / **引用の外の本物の
リダイレクトは見逃さない**）。全体は115件でOK。

## やったこと以外に気づいたこと

- **commitの検出（`GIT_COMMIT_RE`）には引用符落としを当てていない。** 当てると
  `python3 -c "... git commit ..."`のような引用の中の文字列で発火しなくなるが、
  `sh -c "git commit -m x"`のような**本当に走る形**も見逃す。範囲は依頼どおり
  書き込み検出だけに留めた。
- `CR_PUSH_MAX_COMMITS`は記録の関門（既定20）と共用で、こちらは既定50。同じ環境変数で
  両方が動くので、変える時は両方に効くことに注意。
