# 2026-09-18 記録の関門が見るリポを、gitと同じ順で決める

他PCからの改善案（`IMPROVEMENTS.md` 2026-09-18の3件目）。関門が`git -C <パス> commit`で**別のリポを見ていた**。

## 何が間違っていたか

見るリポを「コマンド先頭の`cd`」か「セッションのカレント」だけで決めていた。`-C`は**commitの検出の正規表現には入れてあったのに、判定先を決める箇所で使っていなかった**。

指摘のとおり、これは「git系はパスを毎回明示する」と定めたPJで逆向きに働く。**worktreeのcommitが本体cloneの状態で判定される**ので、worktree側に記録を書いても見えずに止まり（偽の差し戻し）、本体に記録の変更が残っていれば記録なしのcommitが素通りする（偽の通過）。決まりに従っているPJほど当たる。

## 直したこと

- 見るリポを**`git -C <パス>` ＞ 先頭の`cd` ＞ セッションのカレント**の順で決める（gitの実際の挙動と同じ。`-C`が最優先）。
- `-C`の値が変数展開などで**解けない時は判定しない**（exit 0）。別のリポを見て誤るより通す。fail-openの方針どおり。
- 引用符付きのパス（`git -C "/path with space"`）も拾えるよう、検出と抽出でパスの形を共通のパターンにした。
- 差し戻しのメッセージに**どのリポを見たか**を出す（`見たリポ: /path`）。誤判定なら、これだけで分かる。

## 確かめたこと

テスト4件を追加（`-C`の先に記録が無ければ止まる／`-C`は`cd`より優先／`-C`の先に記録があれば通る／解けない`-C`は判定しない）。実セッションでも、使い捨てのリポへ`git -C <パス> commit`を打って、**そのリポの名前を出して止まる**ことを確認した。
