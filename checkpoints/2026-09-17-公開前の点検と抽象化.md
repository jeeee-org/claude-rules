# 2026-09-17 公開前の点検と、業務・個人の具体値の抽象化

このリポを広く配る前提で、公開して困る内容が入っていないかを点検し、濃い箇所を抽象化した。

## 点検の結果

**このリポは点検前からすでにpublic**（`gh repo view`が`"visibility":"PUBLIC"`）。つまり既存の52コミットは公開済みという前提で見た。

- **秘密情報はゼロ**：鍵・トークン・APIキー・パスワード・実メールアドレス・ホーム配下の絶対パスのいずれも無し。コミット著者は全件が`jeeee4 <jeeee4@users.noreply.github.com>`（noreply）。
- **社名・製品名・顧客名・チケット番号・内部URL・内部ホスト名はゼロ**。これ単体で勤務先を特定できる材料は無い。
- ただし**内部の作業慣行が分かる粒度の記述**があった（内部ファイル名・使用ツール名・規約の具体値・社内PCの制約）。ここを抽象化の対象にした。

## 抽象化した箇所

**落とした値そのものはここに書かない。** 対応表の形で残すと、抽象化した意味が無くなる（最初の版でその誤りを犯した）。落とした種類と、置き換え後の書き方だけを残す。

| 種類 | 置き換え後の書き方 |
|---|---|
| 内部ファイル名・スクリプト名 | 「PJ側の文体の学びを集めた文書」「公開手順の機械検査」のように、**役割で書く** |
| 使用ツール名 | 「チャット・課題管理の説明欄・PRの説明・自動応答」のように、**種類で書く** |
| 内部ディレクトリ名 | 「タスクの外にある文書」。テストの作り物は`資料/一覧.md`のような無色の名前へ |
| 規約の具体値（関門の本数・上限のバイト値・レビューの制限） | 「複数の関門で必須」「上限のPJ上書き」「レビューの起こし方の制限」 |
| 社内PCの制約 | 「外部へpushできないPC」 |
| タスクの素性・件数 | 「タスク1つ」「複数のタスク」 |
| 個人の機材 | 保管先・移行先・機材・構成表 |
| テストの値（宅内LANのIP・クラウドストレージ名） | RFC 5737の文書用アドレス（`192.0.2.10`）と、無色の名前 |
| 命名の例 | 機材名を含まない一般的な作業名 |

対象ファイル：`IMPROVEMENTS.md`・`README.md`（経緯）・`PROGRESS.md`・`skills/migrate-rules/SKILL.md`・`checkpoints/`3件・`tools/tests/`2件。

## 判断

- **履歴は1コミットへ畳んだ**。当初は「書き換えない」と判断したが、ユーザーの指示で方針を変えた（履歴の粒度より、過去の版に残る具体値を消すことを取る）。文字列の置換（`git-filter-repo --replace-text`）ではなく過去の版ごと落とす形にしたのは、**置換規則の書き漏れによる取りこぼしが原理的に無い**ため。fork・star・watcherがいずれもゼロで、失うのは54コミットの粒度だけだった。
  - **force pushなので、他PCのcloneは`git fetch && git reset --hard origin/main`か作り直しが要る**（`git pull`では進まない）。
  - **force pushだけでは消えなかった**。畳んだ直後に確かめると、GitHub側では畳む前のコミットがハッシュ指定でまだ読めた（3件とも本文が返った）。到達不能になってもオブジェクトは当面残る。
  - そこで**リポを削除して同名で作り直し**、いまの1コミットをpushし直した。再確認で4件とも404。fork・star・issue・watcherがいずれもゼロだったので失ったものは無く、wikiだけ作成時の既定で有効に戻るため無効へ戻した。**コミットの内容と日時は変えていないのでSHAは`b17adb1`のまま**で、他PCの`git fetch && git reset --hard origin/main`はそのまま使える。
  - 文書が引用しているコミットハッシュ13件のうち、このリポのもの9件は解決できなくなる。READMEの「経緯」の冒頭に断り書きを置いた（当時の識別子としては意味があるので消さない）。
- **redactionの記録に「前 → 後」の対応表を作ってしまい、元の値が公開状態のまま残った**（このcheckpointの最初の版）。落とした種類と置き換え後の書き方だけを残す形に直した。
- **「業務のモノレポ」「業務/共有リポ」という区分の語は残した**。共通ルール（§5.1・§5.2）自体がその区分で書かれており、落とすとルールが指す対象が消える。落としたのは**中身が分かる具体値**だけ。
- **PJ名（kakeibo・disc・voice-input・meeting-scribe）は残した**。どのPJで確かめたかは記録としての根拠で、生活の中身までは出ない。
- **過去の記録を書き換えない流儀の例外**にあたる。事実は保ったまま識別できる細部だけを落としたので、経緯の意味は変えていない。

## 再発を防ぐ決まり

同じ抽象化を毎回やらずに済むよう、**書く時点で効く決まり**を3箇所に置いた（メモを書くのは配布先のPCなので、正本の冒頭だけでは届かない）。

- `IMPROVEMENTS.md`冒頭の書き方の決まりに1行：公開リポに入るので、内部ファイル名・スクリプト名・ツール名・規約の具体値・個人の機材名やIPを書かず、動作で書く。
- `skills/init-rules/SKILL.md`の「改善案の記録」に同じ1行（Claude版）。
- `skills/codex-init-rules/SKILL.md`の同じ節に1文（Codex版）。

## 他PCへの影響

`IMPROVEMENTS.md`の**既存項目を編集した**ので、他PCのcloneに未pushの追記があると、その付近でmergeの衝突が起きうる。他PCでは**追記の前に`git pull`**する。
