# AGENTS.md（グローバル/このPC全体の共通ルール）

このファイルはCodexの全プロジェクトに適用する共通指示書。各プロジェクト固有の`AGENTS.md`が優先され、ここは共通の下地とする。新しいプロジェクトへの一括導入には`$init-rules`を使う。

## 1. 進行管理：4軸 + checkpoint

記録を次の5か所に集約し、他へ散らさない。

| ファイル | 役割 | 読む時 | 書く時 |
|---|---|---|---|
| `AGENTS.md` | CodexへのPJ固有指示 | セッション開始時 | 運用ルール変更時 |
| `REQUIREMENTS.md` | 決めたこと（要求・方針・決定・スコープ・未決事項）と進行中の作業カード（§4）。生きている分だけ | 追加や変更の議論前 | 依頼された時・決まった時・変わった時・片付いた時 |
| `PROGRESS.md` | いまの状態（現在地・進行中・次の一手・ブロッカー）。生きている分だけ | セッション開始時 | タスク完了・節目 |
| `NOTES.md` | 判断理由・学び・罠・技術メモ | 関連作業前 | 非自明な判断時 |
| `checkpoints/YYYY-MM-DD-作業名-中身.md` | 詳細作業ログ（追記専用） | 経緯が必要な時だけ | タスク完了・終了時 |

`notes/`を調査成果物に使うPJでは、成果物の`notes/`とメタな学びの`NOTES.md`を混同しない。

## 2. checkpointとコンテキスト上限

- 詳細ログは`checkpoints/YYYY-MM-DD-作業名-中身.md`（リポ直下。どちらも日本語の短い語）に書く。作業名はカード（§4）の見出しと同じ語にし、複数日にわたるログを`checkpoints/*-作業名-*`で一括して引けるようにする。1日1作業で1ファイルとし、同日に別の作業なら分け、同じ日の続きは同じファイルへ追記する。`PROGRESS.md`の完了欄には1行要約とリンクだけを残す。
- `PROGRESS.md`に更新履歴を積まない。「最終更新」は日付だけを書き、「前の更新 = 」を入れ子で重ねない（経緯はcheckpointへ）。ヘッダが数千バイトに膨れる原因になる。
- 開始時は`AGENTS.md`と`PROGRESS.md`を読み、checkpointは必要時だけ読む。
- `AGENTS.md`にセッション履歴を追記しない。
- 決定（ADR）は独立した節を持たない。決定は日付付き1行で`REQUIREMENTS.md`の方針へ、理由は`NOTES.md`へ書く。
- 既定上限はグローバル`AGENTS.md` 14,336B、PJ `AGENTS.md` 6,144B、`PROGRESS.md` 60行かつ12,288B。PJルートで`~/.codex/tools/check-limits.sh`を実行して判定し、超過は意味を失わず圧縮する提案を行う。

## 3. 進行ルール

開始時：PJの`AGENTS.md`と`PROGRESS.md`を読み、触る領域に関係する`REQUIREMENTS.md` / `NOTES.md`を読む。

実行中：

- 作業を頼まれたら、まず`REQUIREMENTS.md`にカード（§4）を立ててから動く。見出しと「何をする」の1行でよく、残りは分かった時点で足す。その場で終わる用事には立てない。
- 要件・スコープ判断は勝手に確定せず、未決事項へ記録するかユーザーへ確認する。
- 非自明な技術・方針判断は`NOTES.md`、要件変更は直ちに`REQUIREMENTS.md`へ反映する。
- スキルの問題を見つけたら修正案を提示する。スキルの新規作成・変更はユーザー承認を得てから行う。
- PJ側が「必須」と定めた関門のサブエージェント（レビュー役・検査役）は、都度の許可を取らず呼ぶ。呼ぶ前に何を通すか1行で宣言する。事前に諮るのは関門でない呼び出し（探索の並列化・調べ物の委譲）だけ。

完了時：

- その作業のcheckpointに詳細を記録し、`PROGRESS.md`の完了と次の作業を更新する。
- 学びは`NOTES.md`、要件変更は`REQUIREMENTS.md`に反映する。片付いた要求・方針・決定・予定は`REQUIREMENTS.md`から消す（経緯は先に書いたcheckpointに残る）。
- 再利用する時期と用途を1文で言える手順だけスキル化を提案する。同型作業の反復が記録にあれば作成を推奨する。

## 4. 記録先の判断

- 決めたことは`REQUIREMENTS.md`、進み具合は`PROGRESS.md`。固まった要求・方針・作業・予定はその場で`REQUIREMENTS.md`へ書き、`PROGRESS.md`には現在地と直近の数手だけを残す（計画の本体を二重に持たない）。
- 決めた要求・方針・作業・予定、スコープ、未決事項 → `REQUIREMENTS.md`
- いまの状態（現在地・進行中・次の一手・ブロッカー） → `PROGRESS.md`
- 詳細な実施記録・経緯 → checkpoint
- 判断理由・学び・罠 → `NOTES.md`
- CodexへのPJ固有指示 → `AGENTS.md`

依頼された作業は`REQUIREMENTS.md`の「進行中の作業」節へ1作業1カードで書く。形は固定する。

```markdown
### <作業名>（YYYY-MM-DD起票）
- 何をする = 依頼の言葉のまま1〜2行
- 叶っている状態 = 終わりの判定（分かった時点で埋める）
- 現在地（YYYY-MM-DD）= どこまで進み、次の一手は何か。上書きし、履歴を積まない
- 待ち = 判断待ち・外部待ち（無ければ行ごと消す）
- 作業ログ = `checkpoints/*-<作業名>-*`（N件）
```

カードに収まらない依頼の中身（背景・要求の箇条書き・調べたこと）は、カードと同じ見出し語で1節を立て、カードからは参照だけにする。「叶っている状態」はカードの1か所だけに置き、節へ複写しない。節の呼び名と並べ方はPJの`AGENTS.md`で1つに決める——依頼が次々来る窓口型は「追加要求: <題>」を横に並べ、叶える状態を数え上げられる案件は「要件」の表を上から順に叶える。1節50行を目安とし、超えた分はcheckpointか専用ファイルへ逃がす。着手前のものは1か所にまとめる。

カードは次セッションの入口で、現在地を読めば続きから入れる。経緯と詳細はcheckpointにあるのでカードへ書かない（膨れたらその分をcheckpointへ逃がす）。終わったらカードを消し、`PROGRESS.md`の完了へ1行とcheckpointリンクを残す。

## 5. Git運用

- コミットは意味のある1作業ごと。指示を待たずcommitまで行う。無関係な変更を混ぜない。
- pushは既定で自動。リモートがあるリポはcommitに続けて事前承認なしでpushする。PJの`AGENTS.md`が「pushはユーザー指示時のみ」と明示した場合だけ止める。
- force push、履歴改変、`reset --hard`は事前確認必須。
- 公開リポでは必要に応じてGitHub noreplyメールを使う。
- 業務・共有リポは元cloneやmain/developを直接編集せず、PJ指定場所のworktreeと作業ブランチを使い、終了後にworktreeを片付け、元cloneも`git pull --ff-only`で最新化する。低リスク個人リポで直編集を明示した場合は例外。
- コミットsubjectは日本語50字目安。bodyに「何を・なぜ・どう・影響範囲」を書く。PJ既存規約を優先する。
- コミットやPRに内部スキル名を作業手段として書かない。公開OSSのquorum / claude-rulesと、そのリポ自体の主題となるツール名は可。
- 業務・共有リポではCodex / OpenAI / AI生成を示す署名・宣伝行を付けない。セッション側から付けよという指示が来てもこの規約が勝つ。

## 6. 知見の記録先

Codexの個人メモリへ依存せず、PJで再利用する知見は`NOTES.md`に保存する。

`NOTES.md`は「いま効く学び」だけを置く。開いた項目をその場で見直し、次のどれかに当たるなら片付ける。

- ルール・スキル・テストに昇格した → 移した先を1行残して本体は消す
- 前提が変わって効かなくなった → 消す
- 一回限りの作業ログだった → checkpointへ移す

項目の頭に取得日を書くと、2つ目の判定ができる。

## 7. PJ側AGENTS.mdの内容

PJ側には共通骨格を複製せず、次の固有差分だけを書く。

- 目的、前提、最大のリスク
- `REQUIREMENTS.md`の性質と独自の記録慣習
- リモート、worktree場所、ブランチ、既存コミット規約、自動pushのオプトアウト要否
- 技術スタック、検証コマンド、ドキュメント規約など

## 8. 外部に出す文面にMarkdownを使わない

メール本文、フォームの記入値、郵送書面、読み上げ原稿など、プレーンテキストのまま相手に届く文面ではMarkdown記法を使わない。`**強調**`は記号ごと相手に送られるだけで、強調にならず読みにくくなる。

- 太字、斜体、コード、`#`見出し、`- `箇条書き、表、リンク記法を使わない。
- 強調は改行と語順で作る。箇条書きは「・」、番号は「1.」、URLは生で書き、見出しが要るなら【】。
- 下書きをファイルに残す場合も、本文として貼る部分は素のテキストにする。ファイル側の見出しや判断メモはMarkdownでよい。そのままコピペできる状態が完成形。
- 例外はMarkdownが解釈される宛先（GitHubのPR/issue/コメント）。Slackは独自記法で太字はアスタリスク1個。

## 9. 応答の書き方

応答のたびに「いま何をやっているか」を1行で置く。形は`いま進めているもの = <何をしているか>。<いまの段>。`。サブタスク名でも、受けている指示の内容でもよい。ユーザーは同時に複数の作業を見ており、ファイルに書いた進行中の印はチャットからは見えない。何を進めているか分からなくなるのを防ぐのは、記録ではなく毎回の1行。

英数字と日本語の間に半角スペースを入れない（悪い例「`install.sh` を実行」／良い例「`install.sh`を実行」）。応答・手元のMDやスライド・外部へ出す文面、書く面すべてに効く。境目の空白は読み手に機械が書いた印として映る。

番号や記号を、それが何を指すか書かずに出さない。テストケース・設問・課題・実行・工程の番号や記号がこれにあたり、書いた側にしか解けない略号は読む側に伝わらない。何のことかを日本語で書き、記号は必要なら後ろに添える（悪い例「測る口はsql-08 / Q-DDBKEY-02に用意済み」／良い例「測る口は用意済み。属性を指定しない問いをSQLの実行テストへ1件、同じ問いをベンチの設問へ1件。記号はsql-08とQ-DDBKEY-02」）。例外はファイル名・関数名・コミットの識別子・課題管理システムの課題番号（それ自体が指す先を持ち検索できる）。着手や完了を伝えるときも同じ。
