# AGENTS.md（グローバル / このPC全体の共通ルール）

このファイルは Codex の全プロジェクトに適用する共通指示書。各プロジェクト固有の `AGENTS.md` が優先され、ここは共通の下地とする。新しいプロジェクトへの一括導入には `$init-rules` を使う。

ユーザーが「トリアージして」「分類して」「quorum/cadenceが必要か判断して」「適切な進め方を選んで」などと自然言語で依頼した場合は、必ず `$triage` スキルを使う。分類だけを求められた場合は判定だけ返し、「分類してから進めて」と依頼された場合は判定後に本来のタスクを続行する。ユーザーは内部スクリプト名やコマンドを覚える必要はない。

トリアージ分類の意味：

- `T0`: 単純作業・軽い質問。追加フローなしで通常実行する。
- `T1`: 高ステークス×広さ型。並列・多角的レビュー向きで、Codex版 quorum が利用可能なら使う。
- `T2a`: 高ステークス×深さ型。数学、整合性、単一文書などを深く単独検証する。
- `CADENCE`: 完成条件が明確な被覆型の監査・調査・定型修正。Codex版 cadence が利用可能なら対応フローを使う。

## 1. 進行管理：4軸 + checkpoint

記録を次の5か所に集約し、他へ散らさない。

| ファイル | 役割 | 読む時 | 書く時 |
|---|---|---|---|
| `AGENTS.md` | CodexへのPJ固有指示 | セッション開始時 | 運用ルール変更時 |
| `REQUIREMENTS.md` | 要件・調査スコープ・未決事項 | 追加や変更の議論前 | スコープ確定・変更時 |
| `PROGRESS.md` | 現在地・次の作業・ブロッカー・ADR | セッション開始時 | タスク完了・節目 |
| `NOTES.md` | 判断理由・学び・罠・技術メモ | 関連作業前 | 非自明な判断時 |
| `docs/checkpoints/YYYY-MM-DD.md` | 詳細作業ログ（追記専用） | 経緯が必要な時だけ | タスク完了・終了時 |

`notes/` を調査成果物に使うPJでは、成果物の `notes/` とメタな学びの `NOTES.md` を混同しない。

## 2. checkpoint とコンテキスト上限

- 詳細ログは日別 checkpoint に追記し、`PROGRESS.md` の完了欄には1行要約とリンクだけを残す。
- 開始時は `AGENTS.md` と `PROGRESS.md` を読み、checkpoint は必要時だけ読む。
- `AGENTS.md` にセッション履歴を追記しない。
- ADR が10件を超えたら `docs/adr/` への分離を検討する。
- 既定上限はグローバル `AGENTS.md` 14KB、PJ `AGENTS.md` 6KB、`PROGRESS.md` 60行。超過を見つけたら意味を失わず圧縮する提案を行う。

## 3. 進行ルール

開始時：PJの `AGENTS.md` と `PROGRESS.md` を読み、触る領域に関係する `REQUIREMENTS.md` / `NOTES.md` を読む。

実行中：

- 要件・スコープ判断は勝手に確定せず、未決事項へ記録するかユーザーへ確認する。
- 非自明な技術・方針判断は `NOTES.md`、要件変更は直ちに `REQUIREMENTS.md` へ反映する。
- スキルの問題を見つけたら修正案を提示する。スキルの新規作成・変更はユーザー承認を得てから行う。

完了時：

- 当日の checkpoint に詳細を記録し、`PROGRESS.md` の完了と次の作業を更新する。
- 学びは `NOTES.md`、要件変更は `REQUIREMENTS.md` に反映する。
- 再利用する時期と用途を1文で言える手順だけスキル化を提案する。同型作業の反復が記録にあれば作成を推奨する。

## 4. 記録先の判断

- 何を作る・調べるか → `REQUIREMENTS.md`
- 現在地・次の作業 → `PROGRESS.md`
- 詳細な実施記録・経緯 → checkpoint
- 判断理由・学び・罠 → `NOTES.md`
- CodexへのPJ固有指示 → `AGENTS.md`

## 5. Git 運用

- コミットは意味のある1作業ごと。指示を待たず commit まで行う。無関係な変更を混ぜない。
- push は既定で自動。リモートがあるリポは commit に続けて事前承認なしで push する。PJの `AGENTS.md` が「push はユーザー指示時のみ」と明示した場合だけ止める。
- force push、履歴改変、`reset --hard` は事前確認必須。
- 公開リポでは必要に応じて GitHub noreply メールを使う。
- 業務・共有リポは元cloneや main/developを直接編集せず、PJ指定場所の worktree と作業ブランチを使い、終了後に片付ける。低リスク個人リポで直編集を明示した場合は例外。
- コミット subject は日本語50字目安。body に「何を・なぜ・どう・影響範囲」を書く。PJ既存規約を優先する。
- コミットやPRに内部スキル名を作業手段として書かない。公開OSSの quorum / cadence / claude-rules と、そのリポ自体の主題となるツール名は可。
- 業務・共有リポでは Codex / OpenAI / AI生成を示す署名・宣伝行を付けない。

## 6. 知見の記録先

Codexの個人メモリへ依存せず、PJで再利用する知見は `NOTES.md` に保存する。恒常的な知見と一回限りのログを分け、後者は checkpoint へ逃がす。

## 7. PJ側 AGENTS.md の内容

PJ側には共通骨格を複製せず、次の固有差分だけを書く。

- 目的、前提、最大のリスク
- `REQUIREMENTS.md` の性質と独自の記録慣習
- リモート、worktree場所、ブランチ、既存コミット規約、自動pushのオプトアウト要否
- 技術スタック、検証コマンド、ドキュメント規約など

## 8. 外部に出す文面に Markdown を使わない

メール本文、フォームの記入値、郵送書面、読み上げ原稿など、プレーンテキストのまま相手に届く文面では Markdown 記法を使わない。`**強調**` は記号ごと相手に送られるだけで、強調にならず読みにくくなる。

- 太字、斜体、コード、`#` 見出し、`- ` 箇条書き、表、リンク記法を使わない。
- 強調は改行と語順で作る。箇条書きは「・」、番号は「1.」、URLは生で書き、見出しが要るなら【】。
- 下書きをファイルに残す場合も、本文として貼る部分は素のテキストにする。ファイル側の見出しや判断メモは Markdown でよい。そのままコピペできる状態が完成形。
- 例外は Markdown が解釈される宛先（GitHub の PR/issue/コメント）。Slack は独自記法で太字はアスタリスク1個。
