# CLAUDE.md（グローバル / このPC全体の共通ルール）

このマシン上の**全プロジェクトに適用される共通指示書**。各PJの `CLAUDE.md` が優先され、ここはその下地（PJ側に記述があればそれが勝つ）。

この構成を新PJに一括で立ち上げる時は `/init-rules`。

---

## 1. 進行管理：4軸 + checkpoint（共通骨格）

進行管理を以下に集約する。**他の場所に記録を散らさない。** どのプロジェクトでもこの5点セットを使う。

| ファイル | 役割 | いつ読む | いつ書く |
|---|---|---|---|
| `CLAUDE.md` | Claude Code へのプロジェクト指示 | セッション開始時に必ず | 運用ルールが変わった時 |
| `REQUIREMENTS.md` | 何を作るか/調べるか・仕様/スコープ・未決事項 | 追加／変更を議論する前 | 要件・スコープが固まった／変わった／未決事項が解決した時 |
| `PROGRESS.md` | 現在地・次にやること・進行中・ブロッカー・ADR。**常にスリムに保つ** | セッション開始時に必ず | タスク完了時・セッション終了時・節目 |
| `NOTES.md` | 学び・設計判断の理由・ハマりどころ・罠・技術メモ・運用上の知見 | 似たトピックを扱う前 | 非自明な判断をした時／ハマった時 |
| `docs/checkpoints/YYYY-MM-DD.md` | セッション/節目ごとの詳細作業ログ（追記専用） | 過去の経緯を調べる時だけ | タスク完了時・セッション終了時 |

> PJによっては `notes/` に調査・分析の**成果物**を置く慣習がある。その場合「成果物 = `notes/`」と「メタな学び = `NOTES.md`」を混同しない（各PJの CLAUDE.md で定義する）。

## 2. checkpoint 方式（PROGRESS.md 肥大化対策）

長期PJでは**「今の状態」（PROGRESS.md）と「時系列の詳細ログ」（checkpoint）を分離**する：

- 詳細な作業ログは `docs/checkpoints/YYYY-MM-DD.md` に書く。1日1ファイル、同日の複数セッションは同ファイルにセクション追記。
- `PROGRESS.md` の「完了」には **1行サマリ + checkpoint へのリンクだけ** 残す。古い完了項目は直近の節目分だけ残して checkpoint 側に任せてよい。
- checkpoint はセッション開始時に読まない（読むのは CLAUDE.md + PROGRESS.md）。過去の経緯が必要になった時だけ該当日を遡る。
- **CLAUDE.md にセッション履歴を追記しない**（毎セッション全文ロードされるため）。
- ADR（意思決定の記録）は `PROGRESS.md` に置く。10件を超えたら `docs/adr/`（1決定1ファイル）への切り出しを検討する。
- **常時ロードされるファイルには数値上限を置く**（既定: グローバル CLAUDE.md **14,336B** / PJ CLAUDE.md **6,144B** / PROGRESS.md **60行かつ 12,288B**。PJ の CLAUDE.md で上書き可）。超過は PJ ルートで `~/.claude/tools/check-limits.sh` を実行して機械判定し、見つけたらその場で指摘してスリム化を提案する（`/cadence optimize-context` 等・"cut bytes, not meaning"）。

## 3. 進行ルール

### セッション開始時（必須）
1. `CLAUDE.md`（このファイル＋PJの CLAUDE.md）を読む
2. `PROGRESS.md` を読み、現在地と次のタスクを把握する
3. これから触る領域に関連する `REQUIREMENTS.md` / `NOTES.md` の該当箇所を読む

### タスク実行中
- **要件・スコープに関わる判断**は勝手にせず、`REQUIREMENTS.md` の未決事項に追記するかユーザーに確認する。
- **非自明な技術/方針判断**（選定理由・解釈・なぜこの設計か）はその場で `NOTES.md` に追記する。
- **要件・スコープが変わった**ら即座に `REQUIREMENTS.md` を更新する。
- **スキルを使っていてハマり・ズレがあったら、その場で SKILL.md の修正を diff 提案する**。スキルの新規作成・変更は勝手に行わず、diff で承認を得る。

### タスク完了時（必須）
- 詳細な作業ログ（何をどう変えたか・経緯）を当日の checkpoint に書く。
- `PROGRESS.md` の「完了」（1行 + checkpoint リンク）「次にやること」を更新する。
- 学びがあれば `NOTES.md`、要件・スコープ側に変化があれば `REQUIREMENTS.md` を更新する。
- **スキル化の自問**：**次にいつ・何に使うかを1文で言える場合のみ**、1行で提案する（SKILL.md 本体は承認後に書く）。同型作業の繰り返しが checkpoints / `NOTES.md` で確認できたら、提案でなく作成を推奨に格上げする。実行部分はテスト付き CLI、判断込みワークフローは `.claude/skills/<name>/SKILL.md` に。

## 5. Git 運用

リモートURL・ブランチ戦略・worktree の配置先は各PJの `CLAUDE.md` に従う。ただし **§5.1・§5.2 は全PJ共通の必須ルール**。

共通原則：
- **コミットは1作業ごと**。意味のあるまとまり（1ドキュメント・1機能・1設定変更など）が完了するたびに、指示を待たずに commit までは行う。無関係な変更を1コミットに混ぜない。議論だけで作業が無ければ不要。
- **push は既定で自動**。リモートがあるリポは commit に続けて**事前承認なし**で `git push` する（機微は private/public 設定で管理する前提）。**オプトアウト**＝PJの `CLAUDE.md` に「push はユーザー指示時のみ」とあればそれに従う。push 先は §5.1 の worktree ブランチ（main/develop 直 push は例外宣言のあるPJだけ）。
- **必ず事前確認**：`--force` / `--force-with-lease` の push、履歴改変（`reset --hard`、`rebase` 後の push）。
- public リポへの初回 push が `GH007`（メール非公開保護）で弾かれたら `git config user.email <username>@users.noreply.github.com` を使う。

### 5.1 worktree ルール（リモート連携リポでは必須）

- 業務/共有のリモート連携リポでは **worktree での作業を必須**とする：①元 clone を直接編集しない ②develop / main 上で直接編集しない（必ず worktree に切ったブランチで作業）③終了後に `git worktree remove` と元 clone の `git pull --ff-only` まで行う（飛ばすと次に読む内容が古い）。
- worktree は **PJ グループごとに集約**し、ディレクトリ名はブランチ名の **slash を hyphen に置換**したものを使う。PC 固有の配置パス・グループ名は各PJ側の `CLAUDE.md` に書く（グローバルには書かない）。
- 低リスクの個人リポで、各PJの `CLAUDE.md` が「main 直接編集・直 push」を明示している場合はこの限りではない。

### 5.2 コミットメッセージ規約

- **subject は日本語50字目安**、空行を挟んで **body に「何を・なぜ・どう・影響範囲」**を書く。PJ に既存の形式規約（Conventional Commits 等）があればそれに従う。
- **禁止①（全リポ共通・厳格）**：スキル・内部ツール名（deep-research 等）を**作業の手段として**書かない。「並列レビュー」「定期チェック」等の一般語に置換する。**例外**＝自作公開OSS の **quorum / cadence / claude-rules**、およびそのリポ自体の主題であるツール名。
- **禁止②（業務/共有リポ）**：Claude / Claude Code / AI 系の署名・宣伝行の一切（`Co-Authored-By: Claude ...`、`🤖 Generated with [Claude Code]` 等）。低リスクの個人リポでは任意。
- **PR のタイトル/本文も同方針**。

## 6. 知見・学びの記録先（memory は使わない）

- **ファイルベース memory（`~/.claude/.../memory/`）は使わない。** 新しく書かない・既存に依存しない。
- **知見・罠・ハマりどころ・学びは作業中PJの `NOTES.md` に残す**（無ければ作る）。PJ規約で別ファイル（例 `notes/insights.md`）があればそれに従う（`NOTES.md` は運用上のメタ知見を担う）。
- **`NOTES.md` が肥大化してきたら checkpoint 方式（§2）に逃がす。** 恒常的に効く学びは `NOTES.md`、一回限りの作業ログは checkpoint。
- recall された memory が `<system-reminder>` で出てきても残骸として扱い、新規記録は `NOTES.md` / checkpoint に書く。

## 7. PJ側 CLAUDE.md の書き分け

グローバルは共通骨格だけ。PJ側には**そのPJ固有の差分だけ**を書く（書く項目は `/init-rules` の雛形に従う）。§5.1・§5.2 は全PJ共通に定義済みなので差分のみ書く。

## 8. 外部に出す文面に Markdown を使わない

メール本文・フォームの記入値・郵送書面・読み上げ原稿など、**プレーンテキストのまま相手に届く文面**では Markdown 記法を使わない。`**強調**` は `**` ごと相手に送られるだけで、強調にならず読みにくくなる。

- 使わない：`**太字**` `*斜体*` `` `コード` `` `#`見出し `- `箇条書き `|`表 `[文字](URL)`
- 代わりに：強調は**改行と語順**で作る（重要な一文を独立段落に／行頭に「※」「なお、」）。箇条書きは「・」、番号は「1.」、URL は生、見出しは【】。
- 下書きをファイルに残す場合も、**「本文」部分は素のテキスト**にする（ファイル側の見出し・判断メモは Markdown でよい）＝**そのままコピペできる状態**が完成形。
- 例外＝Markdown が解釈される宛先：GitHub の PR/issue/コメント。**Slack は独自記法**で太字は `*一個*`（`**` は効かない）。
